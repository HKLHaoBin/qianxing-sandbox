# 何时优先用 Lua

## 优先 Lua（客户端脚本 + 客户端控件）

下列需求默认走 Lua，不要先规划成物件实体节点图：

- 手牌 / 卡牌 **扇形展开、叠层、露出一角**
- 自定义 HUD、准星、连击条、仅本机可见的提示动画
- 点选、拖拽反馈、控件内过渡动画（在 API 支持范围内）
- 背包式滚动列表、商品列表（用 **GridScroller**，不是扇形）
- 「大多数 2D 玩法」的屏幕交互（官方 7.1 奇匠指南口径）

典型一句判定：*玩家主要在自己的屏幕 UI 上操作，而不是在场景里推一个 3D 物件。*

## 仍用服务端节点图

- 发牌结果、牌堆、出牌是否合法、回合与胜负
- 碰撞、造物、战斗、实体生命周期
- 需要全员一致、防篡改的权威状态
- 元件上的实体逻辑（挂载实体节点图）

## 推荐分工

| 问题 | 放哪 |
|------|------|
| 这张牌在屏幕上的角度、位置、Layer | Lua |
| 这张牌点数/花色贴图内容 | 客户端控件模板 + 脚本改内容 |
| 手牌列表权威数据 | 服务端自定义变量 / 节点图 |
| 点牌后「出牌」是否成功 | 服务端校验；客户端只做乐观反馈 |

## 反例（不要用 Lua 硬扛）

- 用 Lua 代替服务端判定胜负
- 用场景里一排 3D 牌模型模拟手牌扇形（除非刻意做桌面 3D 观感，且接受同步与遮挡成本）
- 用 GridScroller 做扇形角度布局

## 范例：骗子酒馆式手牌

1. **Lua**：按手牌数创建引用控件；按索引算角度与位移；提高右侧 Layer；保证左上角露出。
2. **节点图**：发牌写入玩家手牌数据；出牌请求校验；广播公开信息（出了什么 / 是否质疑成功）。
3. 同步：服务端改手牌数据 → 客户端脚本刷新布局（具体事件/信号以项目设计为准，不在此编造节点名）。
