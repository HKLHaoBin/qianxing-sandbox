# 按整局理解回答元件问题

用户要的是「这个元件现在该怎么做」，不是一份文件名。先建立整局，再落到他问的那张图。

## 找到项目

玩法文档在 `projects/<slug>/`。用户点了名就用那一个。没点名且只有一个正式项目（不含 `_template`）就用那一个。没有正式项目：直接说还没有项目文档，改走 `miliastra-brief`，不要凭通用节点习惯现编这局的步骤。

## 阅读顺序

按这个顺序读，前面的没读就不要回答：

1. `BRIEF.md`
2. `原件清单.md`（全部原件，不只是被问到的那个）
3. `分工.md`
4. `memory-graph.md` 和 `memory/lessons/`
5. 存在则读 `memory/local/`
6. 该原件的 `伪代码.md`，以及被问到的那张（或分工里属于他的全部）`节点图/<图名>.md`
7. 清单里与它有数据来往的相邻原件的职责一句

完成：答得出来这局还有哪些原件、这个原件上下游是谁。说不出上下游，就还没读完。

## 怎么答

用下面的顺序说，每条可核对的事实注明来源路径：

1. 整局里这个原件做什么（BRIEF、原件清单）
2. 对方负责哪些节点图（分工）。用户没限定一张图时，把他名下的图都讲完
3. 每张图：在整局中的位置、按该图文档的步骤做
4. 要改编辑器时，同时遵守 `.cursor/skills/miliastra-node-edit/SKILL.md` 的五要素

节点名拿不准时再查 `.cursor/skills/miliastra-knowledge/SKILL.md`。

## 有据

- 搜索 ID、字段、接线只来自该节点图文档或用户给出的导出。两处冲突时以导出为准，并改文档。
- 文档和导出都没有的 ID：写「文档未记录」。不要用伪代码推一个 ID，也不要靠别的项目的习惯补上。
- 用户问某个节点的问题：先指出文档或记忆里已有的对应条目。两处都没有，就说明这是缺口，问清事实后再把结论写进该节点图文档的「已知问题」。没写进文档之前，不要把猜测说成这局的做法。

完成：回复里的每个 ID 都能指回文件，或明确标成「文档未记录」。
